### Packaging evidence collected during planning

A clean `git archive HEAD` copy in `/tmp` was probed using Python 3.14.4,
pip 25.1.1 and setuptools 78.1.1. A dry-run editable install with dependencies
and build isolation disabled failed during editable metadata preparation:

```text
Multiple top-level packages discovered in a flat-layout: ['specs', 'pyobs_portal'].
```

No package was installed, and portal's checkout was not modified. This proves
a current package-discovery defect, not the exact cause on the reporter's 2.5.5
machine. The installed pip implementation supplies `setuptools.build_meta:__legacy__`
when the build-system table is missing; absence of that table alone is not a
sufficient diagnosis. Setuptools documents the same
[flat-layout discovery restriction](https://setuptools.pypa.io/en/latest/userguide/package_discovery.html#flat-layout).
Full dependency resolution, isolated builds, UI behavior and application tests
remain implementation-time validation; they were not run for this plan.

## 1. Make database configuration consistent

- [ ] In `pyobs_portal/settings.py`, resolve the engine first. For
  `django.db.backends.postgresql`, resolve NAME/USER/PASSWORD from the existing
  `SQL_DATABASE/SQL_USER/SQL_PASSWORD` variables first, then
  `POSTGRES_DB/POSTGRES_USER/POSTGRES_PASSWORD`, then existing defaults. An
  explicitly supplied `SQL_*` value wins, including an empty value; use presence
  semantics rather than `or` fallbacks. Continue using `SQL_HOST/SQL_PORT`.
- [ ] Keep SQLite's current defaults and ignore `POSTGRES_*` aliases when the
  selected engine is SQLite. This avoids accidentally treating a PostgreSQL
  database name as a local SQLite filename. Setting `POSTGRES_DB` alone must not
  switch the engine.
- [ ] Keep the three `POSTGRES_*` entries in `.env.example` as the shared Compose
  credentials. Explain that Django uses them with the PostgreSQL engine; explicit
  `SQL_*` variables are optional overrides for separately managed databases.
  Document both names, precedence, and `DATABASE=postgres` as the container
  entrypoint's readiness flag, distinct from Django's `SQL_ENGINE`.
- [ ] Test settings in a fresh subprocess or isolated settings module without
  a developer's ignored `local_settings.py`: PostgreSQL alias-only, SQL-only,
  both with differing values, explicit-empty precedence, SQLite with no variables,
  and SQLite with stray PostgreSQL aliases. Do not log password values.
- [ ] Render Compose configuration with a disposable example environment and
  confirm web, worker, scheduler and db receive the intended credentials. No
  production credentials or services are needed for this check.

## 3. Enforce task and project priority bounds without silently rewriting data

The contract is a finite float in **[0, 9999]**, including fractional values and
zero. Retain current field requiredness/defaults and non-null storage. Do not
apply these bounds to `Observation.priority`: it stores the scheduler's computed
ranking value, is nullable, and has a different contract.

- [ ] Add reusable finite-number validation plus `MinValueValidator(0)` and
  `MaxValueValidator(9999)` to Project.priority and Task.priority in
  `api/models.py`. Ensure `ProjectSerializer` and `TaskSerializer` expose and
  enforce the bounds on create, PUT and PATCH; add explicit serializer handling
  only if generated fields do not enforce the full contract. Invalid input must
  produce a field-specific 400 before saving anything.
- [ ] Add named database `CheckConstraint`s for both inclusive ranges so writes
  through `save()`, bulk operations or SQL cannot bypass the range. Model
  validators alone do not run on every save. Verify non-finite rejection on both
  SQLite and PostgreSQL; do not assume Python NaN comparisons reject NaN.
- [ ] Add a migration preflight before the constraints using historical models
  and the schema editor's database alias. Detect invalid priorities, including
  non-finite values, and abort with actionable model/count/sample identifiers.
  Do not clamp, set all values to 1, deactivate tasks, or delete data automatically.
  Keep the preflight bounded/streamed for large task tables.
- [ ] Document a pre-upgrade read-only audit and operator repair workflow. Back up
  the database, stop writers for the upgrade, inspect flagged rows, choose valid
  values deliberately, and update through ordinary saves with `updated_at`
  included so scheduler change markers advance. Re-run the audit and migrate.
  Fresh databases and already-valid deployments require no repair. A failed
  preflight must leave existing data unchanged and be safely retryable.
- [ ] Add `min="0"`, `max="9999"`, `step="any"` and meaningful required/validation
  behavior to `frontend/templates/frontend/task_detail.html`,
  `frontend/templates/frontend/admin_projects.html`, and dynamic edit fields in
  `frontend/static/frontend/js/admin_projects.js`. Check validity before JS-driven
  save/clone requests in `taskeditor.js` and project handlers; inputs are not
  submitted through a normal form, so attributes alone are insufficient. Preserve
  zero, reject empty required values, and display server validation errors.
- [ ] Backend coverage: -1, just above 9999, NaN/infinities, null/empty/invalid
  input reject; 0, fractional values, 1 and 9999 round-trip. Cover both models,
  API create/update/partial-update, model validation and constraint enforcement.
  Verify invalid API writes leave stored values/markers unchanged and successful
  priority edits advance the existing task/project marker.
- [ ] Migration coverage: valid rows migrate unchanged; bad legacy rows fail
  preflight clearly; after deliberate repair the migration succeeds; direct ORM
  writes violating constraints fail. Run on SQLite and a disposable PostgreSQL
  instance. Frontend tests cover dynamic project fields, task save and clone,
  especially zero and invalid values. Retain Observation.priority's existing tests.

## 4. Add an explicit pending-observation cancellation action

Add a per-observation action in the task's Schedule tab. Canceling a slot records
`canceled`; it does not deactivate the task, abort an exposure, delete the history,
or promise that the scheduler will never schedule that still-active task again.
Use task deactivation to stop future scheduling of that task.

- [ ] Add `POST /api/observations/<int:pk>/cancel/` in `api/urls.py` and an APIView
  in `api/views.py`. Authenticate with the existing mechanisms. Use the same
  access rule as ObservationDetail: superuser, membership in the observation's
  project, or an authenticated user accessing a public project. Unauthorized or
  missing IDs return 404; anonymous callers get the existing authentication
  rejection. Do not accept a replacement task/project or arbitrary state payload.
- [ ] Resolve authorization through the observation's actual project and perform
  a conditional update restricted to its primary key and `state=pending`, setting
  `state=canceled` and `updated_at=timezone.now()` together. Use a project subquery
  for authorization if needed to avoid duplicate M2M joins in the update. Do not
  read pending and later call an unconditional model save: a worker may have
  changed it to in_progress in between.
- [ ] Return the serialized resulting observation with 200 after cancellation.
  A repeat POST to an already-canceled accessible row is idempotent (200, no
  timestamp change); other non-pending states return 409 with the current state.
  A concurrent deletion returns 404. GET/HEAD on the new route must not mutate
  and should return 405; preserve ordinary OPTIONS behavior.
- [ ] Use `apiRequest()` from `frontend/static/frontend/js/api.js` for the POST,
  retaining session CSRF protection. Add a Cancel action only on pending schedule
  rows in `taskeditor.js` and corresponding table headers in `task_detail.html`.
  Confirm the selected slot, disable its control while the request is pending,
  show failures, and refresh schedule/history after success or a state conflict.
  Keep table column counts, empty states and pagination correct.
- [ ] Include `canceled` and `window_expired` in the task's observation-history
  query, which currently only requests completed/aborted/failed. A canceled row
  should remain visible in history with its state and no inappropriate archive
  action. The existing 14-day cleanup policy still applies to canceled/expired rows.
- [ ] Keep `cancel_pending_observations()` and the existing signal tests. Extend
  coverage through an actual API task deactivation and its update marker. Task
  deletion currently cascades and removes observation rows despite the pre-delete
  signal; do not claim it retains canceled history or change deletion semantics.
  For old inactive tasks with stale pending rows, document an optional explicit
  one-time reconciliation using the existing helper; do not silently rewrite
  historical observations during startup or migration.
- [ ] Tests cover member/public/superuser access, unrelated-project 404, anonymous
  rejection, session requests with missing and valid CSRF, POST-only behavior,
  idempotency, timestamps/marker visibility, and every non-pending state. Exercise
  a worker state change between lookup and conditional update to show the action
  cannot overwrite an already-started row. Add Vitest coverage for button visibility,
  confirmation, POST method, disabled state, success refresh, conflict and failure.

The legacy `/api/cancel_observations/?after=...` GET route is consumed by core's
`PortalObservationArchive` and must not be repurposed as the new browser action or
removed as part of this issue. Migrating that route to a safe method requires a
separate coordinated compatibility change. Similarly, this action does not create
a distributed execution lock: the existing generic observation updater and an
already-running telescope process are separate paths. Verify the conditional-update
ordering honestly; preventing every possible stale worker write or physically
stopping a running observation is outside this issue.

## 5. Document and verify a complete no-Docker local workflow

  `CELERY_TASK_ALWAYS_EAGER` and `CELERY_TASK_EAGER_PROPAGATES`, using the existing
  `"1"` boolean convention and false defaults. Local Python settings overrides
  continue to work. Set both flags to 1 in the local guide so cleanup runs in its
  caller and failures surface during development. Leave production's broker-based
  defaults unchanged; no new scheduler or automatic worker startup is needed.
- [ ] Expand `docs/source/development.rst` with one copyable path using Python
  >=3.12, a venv and `python -m pip install -e .`, plus the equivalent existing uv
  workflow (`uv sync --locked`, `uv run ...`). Explicitly activate the venv for
  pip commands and run from the source checkout. Explain the supported local
  configuration rather than telling users to copy the Docker `.env` unchanged.
- [ ] Show a complete development environment: frontend enabled, DEBUG=1,
  localhost/127.0.0.1 allowed, development-only secret, SQLite engine and an
  explicit writable absolute database path, writable static root, both eager flags
  enabled, `CELERY_BROKER_URL=memory://` and
  `CELERY_RESULT_BACKEND=cache+memory://`. Give site coordinates as optional
  site-specific values for the dashboard. No Keycloak, archive, web-admin or
  telescope hardware is required to log in and create projects/tasks.
- [ ] State that Django does not automatically read `.env`. Use shell exports in
  the main recipe, or explicitly show uv's `--env-file` option/local_settings.py
  as alternatives. The web and scheduler processes must receive the same settings
  and SQLite path. Document that `local_settings.py` overrides environment-derived
  settings, and distinguish `FRONTEND_ENABLED` there from `ENABLE_FRONTEND` in env.
- [ ] Include migrate, createsuperuser, runserver on `127.0.0.1:8000`, login/UI/API
  URLs, and `collectstatic --noinput` for installed-package or DEBUG=0 verification.
  Node/npm are needed for frontend tests, not to build assets just to run the UI.
  State that internet-hosted UI assets and optional remote lookups are distinct
  from the absence of Docker/database/broker services; do not promise offline UI.
- [ ] Start a second process with the same environment:
  `python manage.py runscript pyobs_portal.task_scheduler` (or `uv run python ...`).
  Existing `task_scheduler.py` invokes `mark_window_expired.delay()` every five
  minutes and `delete_old_observations.delay()` hourly; eager mode executes these
  directly in that process. Run a single such scheduler for the local database.
  Eager mode supplies neither a clock nor durable background processing, and no
  Celery worker/beat/RabbitMQ process is needed for this recipe.
- [ ] Explain the manual immediate check `python manage.py mark_window_expired`.
  It works without a broker; running it once does not replace periodic cleanup.
  Document the existing retention policy: canceled/window-expired observations
  older than 14 days are deleted, at most 100,000 per cleanup invocation.
- [ ] Update README, `docs/source/installation.rst` and
  `docs/source/configuration.rst` to link the local recipe and describe eager
  settings/environment precedence. Add cancellation and priority behavior to
  `docs/source/frontend.rst` and `docs/source/api.rst`. Keep Docker Compose as the
  existing production recommendation; SQLite/eager is a local/test setup, not a
  newly promised multiworker production deployment model.
- [ ] Test eager settings through real environment loading, including flags unset
  and set to 0/1. In a temporary database, call the actual task `.delay()` paths
  with eager configured: expired pending becomes window_expired; in-progress and
  future pending remain unchanged; old canceled/expired rows are pruned according
  to retention while completed history stays. Arrange the test to fail if a
  network broker connection is attempted. Test scheduler job registration without
  waiting for wall-clock minutes or starting an unbounded loop.
